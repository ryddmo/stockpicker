# Adversarial Seam Review — Stockpicker Architecture Spine

## Overall verdict
Two implementers each following this spine to the letter can still produce incompatible systems, mainly because the Pipeline↔Web seam leans on one undefined artifact (`owner_count_metrics`) and two new-layer ADs (AD-13 auth failure, AD-3/AD-15 entity ownership) don't account for each other's edge cases.

## Findings

- **critical** `Deriver` (Pipeline, K10/AD-3/AD-11) vs `LeaderboardController`/`StockDetailController` (Web, AD-14/K18) on what `owner_count_metrics` *is*. K10's capability map calls it "**vyn** owner_count_metrics" (a SQL VIEW), the AD-11 nightly sequence diagram has Deriver "materialisera/uppdatera härledda mått" (implying a persisted table Deriver writes to), and the human-page sequence diagram has `StockDetailController` fetch "båda källors fullständiga serier ur owner_count_metrics" per source. A Pipeline implementer who takes "vyn" literally creates `CREATE VIEW owner_count_metrics AS SELECT … window functions` — which is non-updatable in MariaDB, making Deriver's nightly step a no-op with nothing to upsert, contradicting AD-11's requirement that Deriver produce loggable run stats. A different implementer, following the sequence diagram, creates a real table and writes upsert logic into it. Both are literal readings of the same spine and yield incompatible DDL. Worse, the *grain* of this object (one row per `isin`, or per `isin, source, as_of_date` matching `owner_count_daily`'s natural key) is never pinned anywhere — yet K18 requires per-source full series, which is only possible if the grain includes `source`. The Deferred section frames this as a routine "column types/indexes" detail, but the grain is load-bearing for K18, not a deferred implementation nicety. *Fix:* New AD (or amend AD-3/K10) that: (1) states explicitly `owner_count_metrics` is a persisted table populated by `Deriver` via upsert, not a live SQL view — rename it if the "vy" wording must stay UI-facing terminology; (2) pins its natural key as `(isin, source, as_of_date)`; (3) moves this out of "Deferred" since it is architecturally load-bearing, not a migration detail.

- **high** `UniverseSync` (Pipeline, AD-3 + K1b "borttagna bolag") vs `WatchlistRepository` (Web, AD-15 "the only writer to `watchlist`, first non-pipeline write path") collide over a delisted, starred instrument. AD-11 confirms UniverseSync actually removes companies from `instrument` ("loggar antal … borttagna … bolag"), but nothing says whether that's a hard `DELETE` or a soft-delete/status flag, and the ER diagram's FK `instrument ||--o{ watchlist` doesn't state an `ON DELETE` policy. A Pipeline implementer doing a literal hard delete either needs `ON DELETE CASCADE` (which makes a nightly Pipeline run silently mutate a table AD-15 declares is Web-exclusive) or `ON DELETE RESTRICT` (which silently breaks K1b's reconciliation the moment a user has starred a stock that gets delisted) — and a Web implementer building `WatchlistRepository` in isolation has no reason to anticipate either outcome. *Fix:* New AD pinning instrument removal to a soft-delete/status column (never a hard `DELETE` while FKs from `watchlist`/`work_queue` exist), and stating explicitly that a cascade-triggered watchlist row change is not a violation of AD-15's sole-writer rule — or, if hard delete is intended, requiring `UniverseSync` to first evict matching `watchlist` rows through `WatchlistRepository` (making the exception to AD-15 explicit rather than implicit).

- **high** `AuthController`'s shared cookie-validation contract (AD-13: on failure, "tyst till inloggningsformuläret" / render login form with "Session expired") vs `WatchlistController`'s `fetch()` toggle endpoint (AD-12: "den enda platsen i systemet med en JSON-liknande respons utanför HTML-rendering"). AD-13 binds "alla människovända routes" and prescribes rendering the HTML login form on any auth failure — but the star-toggle endpoint is invoked via `fetch()` from `watchlist.js` expecting a small JSON-like body, not an HTML page. An implementer following AD-13 literally for every route (including the toggle endpoint) makes an expired/invalid session return an HTML login page to an XHR call, which `watchlist.js` has no code path to parse — the star silently fails to update with no error surfaced, while a different implementer building `WatchlistController` off AD-12's "JSON-like response" framing would special-case auth failure into a 401 + minimal body. Nothing in the spine tells either which is correct. *Fix:* Tighten AD-13 (or add a clause to AD-12) defining a distinct, non-HTML auth-failure contract for the toggle endpoint specifically (e.g., HTTP 401 with the same minimal response shape as success), and require `watchlist.js` to handle it.

- **medium** `LeaderboardController`/`FullListController` (Web) vs AD-8's config convention on where UI *defaults* live. AD-8 binds "**all** kod som läser konfiguration" and requires operational parameters to live in `settings` and be "läsas vid varje körning" (read on every run). AD-14 separately declares the UI's default values (source=Avanza, ranking=Most Owners, interval=Day, sort=owner-count-desc) to be hardcoded per-request fallbacks in the controller classes, explicitly not stored preference. Nothing scopes AD-8's "all" away from these Web-layer defaults, so an implementer reading AD-8 first could reasonably source "default ranking mode" from `settings` (it plausibly is an "operational parameter" changeable without deploy), while a colleague building `FullListController` off AD-14 hardcodes a PHP literal — leaving two different single-sources-of-truth for what should be one consistent default policy, and no way for an operator to know which mechanism actually controls behavior. *Fix:* Add one sentence to AD-8 excluding Web-layer interaction defaults ("governed by AD-14 instead"), closing the overlap explicitly.

- **medium** No shared error-rendering unit is named across `src/Web/` controllers. AD-14 says an uncaught exception is "fångas på samma sätt som cron-routens `catch (\Throwable)` idag … renderar en generisk felsida" but never states whether that catch lives once in the front controller (shared) or is duplicated inside each of `LeaderboardController`, `FullListController`, `StockDetailController`, `WatchlistController` individually — nor pins an HTTP status code or template. Two controllers built independently from this spine can each satisfy AD-14's letter while rendering different markup and status codes for the same failure class (e.g., one returns 500 with a styled page, another returns 200 with an inline "something went wrong" div). *Fix:* Add a Consistency Conventions row (or amend AD-14) naming the single shared error-rendering point — front controller catch block or one `src/Web/` helper — and the HTTP status it must return.

- **low** The `source` query-parameter's on-the-wire value/casing convention (`avanza`/`nordnet` vs `Avanza`/`Nordnet`) is used by three independently-built controllers (`LeaderboardController`, `FullListController`, `StockDetailController`) but never fixed in Consistency Conventions, only implied by the `owner_count_daily.source` column values. *Fix:* Add a Consistency Conventions row pinning the query-string value to the lowercase source-column value, so all three controllers parse/generate links identically.
